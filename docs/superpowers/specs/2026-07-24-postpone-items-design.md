# Missed Work and Postpone Design

## Purpose

The Planner records work that was not completed on its scheduled date. A
single `Miss` control offers two outcomes:

- mark the scheduled work as missed;
- mark it as missed and create a new independent follow-up for the user's
  local next calendar day.

The design supports ordinary tasks, events, and tasks generated by routines.

## Status Model

`missed` is a terminal item status meaning the work was not completed on its
scheduled date. It is visible by default; Planner and Workspace status filters
and status groups include it so users control whether it is shown.

`someday` is removed from the status model. Schema initialization migrates
existing `someday` rows to `missed` before normal item queries run.

## Actions

### Miss

`Miss` changes an eligible task or event to `missed`, retains its original
`scheduled` value, and writes an audit event. It creates no follow-up.

### Miss and postpone

`Miss and postpone` performs `Miss` and creates an active follow-up item for
the browser's local next calendar day. The client sends that ISO date
explicitly so the scheduled result cannot depend on the API process timezone.

The follow-up keeps the source type (`task` or `event`) and copies its title,
description, note, tags, priority, area, project, parent, and `due` value. It
stores `postponed_from`; the source stores `postponed_to`.

Only active task and event rows expose the Planner `Miss` action. Routine
templates and terminal items are not eligible.

## Routine Semantics

For a routine-generated task, either action records the source occurrence as
`missed` and refills the routine's configured occurrence target. The follow-up
from `Miss and postpone` is an independent task: it has no `routine_id`, no
`occurrence_key`, and no `metadata.generated_by` marker.

The source transition, any follow-up, routine occurrence record, replenished
routine task, and their audit events are one atomic SQLite operation.

## Planner Interaction

Daily, Weekly, and Monthly rows expose one compact `Miss` button beside the
completion checkbox. Clicking it opens a dialog with:

- `Mark missed`;
- `Miss and postpone`;
- `Cancel`.

The dialog has no date field. The item detail panel has no miss or postpone
property control.

## Interfaces and Errors

The service exposes separate miss and postpone actions. HTTP and CLI expose
both actions for automation, while the Planner uses the `Miss` dialog.

The actions reject missing items, unsupported item types, and terminal source
statuses. Persisted action results contain the updated source; postpone also
returns its follow-up.

## Verification

Tests cover:

- schema migration from `someday` to `missed`;
- status parsing, filtering, grouping, and default Planner visibility;
- ordinary task and event miss/postpone actions;
- browser-local explicit tomorrow dates even when the API process timezone
  differs;
- routine occurrence recording, replenishment, detachment, audit events, and
  transaction rollback;
- Planner dialog choices and absence of the former detail date control.
